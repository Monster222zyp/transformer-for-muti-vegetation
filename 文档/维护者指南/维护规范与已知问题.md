# 维护规范与已知问题

## 1. 维护原则

### 1.1 保持物理语义可追溯

任何数据和结果都应能回答：来自哪次实验、使用什么构型、何种角度和速度、经过哪些处理参数、由哪个配置训练。无法回答这些问题的副本只能作为临时工作文件，不能升级为正式基线。

### 1.2 上游变化必须重建下游

依赖关系如下：

```text
构型 / 原始数据 / 物理配置 / 处理参数
                ↓
       filtered_data 与汇总数据
                ↓
          模型训练与指标
                ↓
            可视化结果
```

改变任一上游含义后，不应继续沿用旧下游产物并假装可比较。

### 1.3 结果必须带划分语义

报告指标时至少同时写明：输入数据版本、样本数、`split_mode`、fold 数、validation/test 是否重叠、是否为 held-out、是否做 final retraining。

## 2. 当前已知的高优先级不一致

### 2.1 默认训练数据与正式汇总输出不同

`model/configs/base.yaml` 当前指向根目录 249 条 `dataset.jsonl`，而正式汇总脚本输出 `Experiment/output/dataset.jsonl`，当前为 332 条。

影响：直接运行 `python -m model.train` 不会使用 0.1 m/s 数据，也不会自动使用刚刚重建的 `Experiment/output/dataset.jsonl`。

维护建议：每次训练显式传 `--data`；项目负责人随后决定是否把 `base.yaml` 改为可移植的正式默认路径。

### 2.2 数据路径包含本机绝对路径

`model/configs/base.yaml` 和 `visualization/config.yaml` 当前包含 `C:\Users\Mayn\...` 形式的路径。

影响：仓库迁移到其他用户、磁盘或操作系统后无法直接运行；历史 `resolved_config.json` 中保留绝对路径属于正常快照，但源配置不具可移植性。

维护建议：源配置优先使用相对项目根的路径，运行时再解析为绝对路径；修改前先确认现有脚本的路径解析规则和测试。

### 2.3 构型基线有两份

`Experiment/input.csv` 被忽略，`Experiment/input copy.csv` 被追踪，当前内容相同，但没有规定哪一份是唯一真源。

影响：一份被修改后，数据汇总和版本控制记录可能分离。

维护建议：指定被追踪的规范文件，或增加显式同步/校验步骤；在完成决定前不要删除任何一份。

### 2.4 完整 JSONL 有多个副本

`Experiment/output/dataset.jsonl` 与未追踪的 `dataset_initial.jsonl` 当前完全相同，根目录另有 249 条工作副本。

影响：文件名没有表达完整/筛选/日期/处理版本，维护者容易选错。

维护建议：引入数据 manifest 和有意义的版本命名，例如完整基线、去除某速度的实验子集、外部评估集分别记录。

### 2.5 依赖清单不完整

`model/requirements.txt` 不包含 `Experiment/filter_sensor_data.py` 需要的 SciPy，仓库也没有统一 lock file。

影响：只按 requirements 安装后，正式数据链第一步仍会因缺包失败；不同环境可能产生细微数值差异。

维护建议：建立项目级依赖文件和可复现环境说明，同时区分 CPU/GPU PyTorch 安装方式。

### 2.6 当前源配置与现有训练产物已经漂移

现有 `model/artifacts/resolved_config.json` 记录 `mirror_augmentation: false`，而当前工作区 `model/configs/base.yaml` 已经是 `mirror_augmentation: true`。

影响：即使使用相同数据和随机种子，直接重跑当前默认配置也不是对现有 artifact 的精确复现。

维护建议：解释历史结果始终读取该结果目录的 `resolved_config.json`；新训练使用新目录，并把源配置变化写入运行记录。

## 3. 可视化工具的已知问题

| 问题 | 影响 | 当前规避方式 |
|---|---|---|
| `visualization/config.yaml` 写有绝对路径 | 换机器即失效 | 运行前复制并修改配置 |
| `plot_split_drag_comparison.py` 默认输入指向根级 `artifacts/` | 找不到模型默认输出 | 显式传 `model/artifacts/.../test_predictions.csv` |
| 该切图脚本的帮助文本与实际部分默认值不一致 | 标题或输出位置可能不符合预期 | 显式传输入、`--output-dir` 和 `--title` |
| `plot_nonzero_distribution.py` 硬编码本机路径 | 迁移失败 | 运行前修改路径；后续应增加 CLI |
| `plot_nonzero_distribution.py` 导入即执行 | 作为模块导入会产生文件 | 只作为独立脚本运行 |
| 两个速度筛选器默认寻找不存在的 `visualization/dataset.jsonl` | 省略参数会失败 | 先复制源文件，再显式传工作副本 |
| 两个速度筛选器原地覆盖 | 可能损坏唯一数据 | 永远对副本运行 |
| 逐株绘图会清空输出目录 | 其他图片可能被删除 | 使用专用的新输出目录 |
| 当前 `visualization/output/` 没有独立 manifest | 无法仅凭目录证明使用了哪个 checkpoint | 归档时记录 checkpoint、数据哈希和配置 |

## 4. 实验脚本的已知问题

| 问题 | 影响 | 当前规避方式 |
|---|---|---|
| 4 个 sensor 原始记录过短 | 只能得到 332/336 条现有条件 | 保留缺失清单，不补零、不插值整条条件 |
| sensor 与运动轨迹没有同步偏移记录 | 不能严格对齐两个时间轴 | 只把分析窗口解释为相对 sensor 起点 |
| adapter 检查 x 的有符号和 | 不等于绝对累计路程 | 实验前人工复核轨迹范围 |
| adapter 成功时可能保留旧高编号文件 | 设备目录可能混入旧轨迹 | 运行后核对 `mapping.json` 和文件数 |
| 构型重建会改变随机布局 | 已有实验标签可能全部错配 | 不在日常流程运行 `--overwrite` |
| `--row` 不限制旋转图批量导出 | 产生比预期更多图 | 将它只理解为总览筛选参数 |

## 5. 模型与评估的解释风险

### 5.1 `flow_speed` 的 test 不独立

该模式使用 0.1/0.2/0.3 m/s 训练，将完整 0.4 m/s 同时用于 early stopping 的 validation 和 test。它适合观察跨速度外推，但 test 指标已经参与模型选择，必须标注 `validation_test_overlap`。

### 5.2 `sample` 划分可能泄漏构型信息

相同 `model_id` 的不同角度和流速高度相关。逐行随机切分可能让同一几何构型同时出现于训练和测试，不能代替按 `model` 或 `plant_count` 的更严格泛化实验。

### 5.3 final 模型的原数据评估是 in-sample

普通 CV 结束后，final 模型用全部数据重训。它适合部署，但在同一数据上的评估只说明拟合情况；正式泛化结论应来自交叉验证各折的 held-out test 聚合。

### 5.4 逐株 coefficient 不可识别为真实力

训练只监督总 `FX_0`，没有逐株标签。许多不同的逐株系数组合可能产生相同总和，因此 `latent_coefficient` 是解释性潜变量，不是唯一可识别的真实单株阻力。

### 5.5 负标签被截断

当前 `negative_target_policy: clamp_to_zero` 让训练使用 `max(FX_0, 0)`，同时保留 `raw_target_drag`。发布结果时应说明这一处理，并在获得传感器不确定度后重新判断负值是噪声、零点偏移还是有效反向力。

## 6. 目前缺失的实验元数据

高优先级待补：

- 水草材料、形状、尺寸、柔性、浸没深度；
- 格点真实间距；
- 传感器型号、量程、精度、采样配置和各轴单位；
- `ang0` 装置参考方向；
- 传感器与运动控制触发同步；
- 去皮、静水、空载、装置阻力和漂移处理；
- 实验日期、操作者、设备配置、重复次数；
- 原始文件的验收规则和异常记录。

建议新增不可变的实验批次 manifest，例如 CSV、JSON 或 YAML，每批至少包含上述信息以及源文件哈希。

## 7. 修改不同内容时要联动什么

| 修改内容 | 必须同步核对 |
|---|---|
| 六边形编号、坐标或旋转规则 | `input.csv`、构型生成、汇总、模型几何、可视化、几何测试 |
| sensor 文件命名或速度映射 | filter、summarize、缺失清单、数据测试、文档 |
| 六轴列顺序或单位 | 原始数据说明、filter、summarize、旧数据迁移、物理报告 |
| 滤波或截尾参数 | 全部派生数据、训练结果、处理版本和结果报告 |
| JSONL schema | summarizer、dataset loader、evaluate、visualization、测试、schema version |
| `physical.yaml` | 新训练、外部数据覆盖范围、物理说明；历史 checkpoint 不自动改变 |
| split mode | 独立实验 YAML、结果目录、指标解释和对比表 |
| 负标签策略 | 数据加载、loss、预测表解释和历史结果可比性 |
| artifact 目录策略 | 清理安全测试、归档流程和运行说明 |

## 8. 安全维护流程

### 8.1 开始修改前

1. 运行 `git status --short`，区分已有用户修改与本次工作。
2. 记录将使用的数据文件、行数、流速分布和哈希。
3. 为本次实验建立独立配置与 artifact 目录。
4. 对会原地覆盖的脚本准备副本。

### 8.2 修改后

1. 运行相关专项测试，再运行 `python -m pytest model/tests -q`。
2. 对 CSV/JSONL 验证字段、行数、唯一 ID、有限数和分组分布。
3. 用 overfit 检查整个训练通路。
4. 检查 `resolved_config.json` 是否符合预期。
5. 检查留出集合语义和数据泄漏。
6. 更新相应目录 README 与本维护者指南。

### 8.3 结果归档

1. 保存 Git commit 与未提交修改说明。
2. 保存数据版本和哈希，不只保存路径。
3. 保存 resolved config、fold assignments、metrics 和 predictions。
4. 记录 Python、PyTorch、CUDA 和依赖版本。
5. 把物理结论与模型假设、留出协议、样本局限一起写入报告。

## 9. 推荐的后续维护改进

按优先级建议：

1. 确定并版本化唯一构型基线。
2. 给完整数据与各筛选子集建立 manifest 和清晰名称。
3. 把源配置中的绝对路径改为可移植路径。
4. 建立覆盖 Experiment 与 model 的统一依赖文件/lock file。
5. 给可视化脚本补齐 CLI，并移除导入副作用。
6. 让所有破坏性脚本默认输出到新文件，只有显式参数才原地覆盖。
7. 补充实验设备、单位、同步和校准元数据。
8. 增加独立重复实验，用于估计实验噪声和判断负标签。

这些建议不是当前运行前置条件，但会显著降低未来接手、复现和科学解释的风险。
